# Employee codes and monthly evidence release

## Scope and architecture

Independent employee codes are generated by a PostgreSQL sequence and protected by a trigger and unique/format constraints. UUID remains the key and employee_number/Person Code remain device identifiers. The backfill adds a volatile-default column without firing employee UPDATE/audit triggers. Codes are immutable and issued sequence values are not reused.

The new monthly evidence RPC reads an explicit monthly import, or the single approved/applied import for official views. A shared pure calculation serves immediate inspection, saved preview, approved matrix, dashboard, employee detail and exports. It never reads daily punches into monthly totals. Overlap is disclosed without double counting. Raw calendar evidence and review decisions are unchanged.

Shift pairing uses actual dated entry windows: first valid entry and last subsequent punch before the next workday's entry window. It cannot consume the next afternoon entry, reuse a punch, or transform a morning calendar punch into a fabricated future exit. Missing rules and boundary evidence remain explicit. No guessed duration cap, absence, leave or deduction policy is added.

## Security assessment

Updated vulnerable production framework dependencies to compatible patched versions: Next16.3.6, React/ReactDOM/RSC19.2.8, Vite8.3.1, and targeted compatible transitive patches. Runtime-only npm audit returned zero advisories. Both runtime and complete audit results are retained outside source artifacts.

The complete audit still reports **12 dependency entries: eight high and four moderate**, all in development/build dependencies. Their reachability was inspected rather than dismissed:

- Cloudflare plugin/Miniflare/Wrangler and their pinned ws, undici, sharp have development-server/network/image-processing advisories. Those Node-based local tools are not the hosted Worker. No public development server, proxy, or untrusted image conversion is used in production.
- drizzle-kit/esbuild-kit's older esbuild has development-server origin/Windows file-read advisories; this release does not run that esbuild server or Drizzle migrations against production.
- vinext's pinned image-size2.0.2 has high-severity malformed JXL/HEIF/ICNS infinite-loop advisories. The installed call sites read repository-owned images/metadata during build; the generated server artifact does not contain image-size/metadata-route-build-data. User XLS uploads do not reach these parsers. The suggested framework beta/major migration was not applied automatically.

These are unresolved toolchain maintenance risks, not a clean full dependency audit. Do not expose the local build/dev services or build untrusted image assets. Relevant sources: [image-size](https://github.com/advisories/GHSA-5p2g-fcmc-qvqq), [esbuild](https://github.com/advisories/GHSA-g7r4-m6w7-qqqr), [RSC patched DoS](https://github.com/advisories/GHSA-wx67-qw84-cm4g).

Database access remains role-checked RPC access with active-profile checks, empty function search_path, no anonymous/public execution on new RPCs, no direct table-write grants, and immutable audit. Existing RLS-without-policy notices reflect intentionally denied direct table access; permissive policies were not added. The managed `rls_auto_enable` event-trigger function is not an ordinary client RPC; its provider-owned behavior was not rewritten. Existing profiles auth.uid() per-row and attribution-column index advisors remain measured-maintenance candidates; audit/index history was not deleted.

Leaked-password protection remains unavailable on the current Free plan; [Supabase documents Pro-plan availability](https://supabase.com/docs/guides/auth/password-security). No paid plan, authentication bypass, session-secret extraction, or password change was performed.

Production application is gated on exact clean Git HEAD, checkpoint hashes and immediate full-content/history comparison under bounded native locks, then target-only atomic SQL/history and read-only verification. Recovery preference is to roll back the UI version while retaining additive schema/codes. Never reset the code sequence or regenerate issued codes. A production backup restore is not automatic: it would lose post-checkpoint legitimate writes. Any disaster recovery after new codes are issued must preserve the latest code mapping/sequence and all intervening business/audit changes.

Release status, exact source commits, production migration result and authenticated live outcomes belong to the final retained release report, not an assumption from local tests.
